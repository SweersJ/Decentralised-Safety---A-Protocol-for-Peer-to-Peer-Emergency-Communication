# Introduction

This project provides the formal verification setup of an emergency communication protocol for decentralised networks. Specifically the synchronisation of messages of the network where the nodes have intermittent connectivity. Therefore, messages are stored on the nodes and synced when possible. Furthermore, the messages are given specific priorities to setup a reliable communication for several emergency communicators, such as emergency dispatchers and in-field emergency responders. Next to that civilians, will also be able to utilise the protocol, but with lower priorities.

The project is part of the Master thesis assignment, named 'Decentralised Safety: A Protocol for Peer-to-Peer Emergency Communication'

# Project structure

The project is structured based on versions of the models. These versions can be found in the subfolders of the versions folder. The documentation of the versions can be found in the markdown file [versions](versions.md). The subfolders are named with the version number. The internal folders are the different states for that version. The first folder `00` contains the test example scripts. In the subfolders you will find the following:
- a quint file with extension `.qnt`
- a markdown file with the same name as the quint file
- Optionally: a TLA file with extension `.tla` of the compiled quint file into TLA specification. This generated by `quint compile <file> --target tlaplus --out <name>.json`, the standard output provides the TLA file.
- Optionally: a json file with the determined structure of the quint file. This generated by `quint compile <file> --target tlaplus --out <name>.json`.
- Optionally: mermaid diagrams describing the sequences and states described by the quint file.

# Tools

In this project their has been chosen for quint as formal verification tool as it is close related to actual written code, such as python instead of the default notation of LTL/CTL formal verification proofs. This makes it easier to convert code into a formal model. Quint has as basis the TLA+ formal verification language.

- Traffic light:
	```quint
	module trafficLight {
	    // A state variable to store the current color
	    var color: str
	    
	    // The initial state of the traffic light
	    action init = {
	        color' = "red"
	    }
	    
        // An action that can be taken to a new state
	    action toGreen() = all {
		    // A precondition, to see whether the color is in the correct state
		    color == "red",
		    // The action to turn traffic light to green
		    color' = "green"
	    }
	    
	    action toYellow() = all {
		    color == "green",
		    color' = "yellow"
	    }
	    
	    action toRed() = all {
		    color == "yellow",
		    color' = "red"
	    }
	    
        // The steps to be taken at any given moment
	    action step() = any {
		    toGreen,
		    toYellow,
		    toRed
	    }
	    
	    // Invariant check if the correct colors are used at each state
	    val validColor = color.in(Set("red","yellow","green"))

        temporal eventuallyEveryColorOnce =
            // Assuming fair execution (step is always eventually taken when enabled),
            // the traffic light should always eventually cycle through all colors
            step.weakFair(Set(color)) implies (
                always(eventually(color == "green")) and
                always(eventually(color == "yellow")) and
                always(eventually(color == "red"))
            )
        }

    	run greenYellowRedOrderTest = init.then(toGreen).then(toYellow).then(toRed)
	```

# How to run and why?

- To look for violations of this invariant, we can use the run subcommand, which will simulate a bunch of executions while checking the invariant.
	```cmd
	quint run versions/00-test/bank.qnt
	quint run versions/00-test/bank.qnt --mbt --n-traces=10000 --out-itf=traces/out.itf.json
	```

    - Optional: `--mbt` says we want extra info in the traces that is very useful for model-based testing
    - Optional: `--n-traces` determines how many traces the simulator will hold in memory. It will hold the N longest traces in case there is no violation, or the shortest ones if they represent violations to given properties (not the case in this example)
    - Optional: `--out-itf` specifies that we want to dump all those traces to JSON, and where to put them.

-  Run the testing for a specific invariant
    ```cmd
    quint run versions/00/bank/bank.qnt --invariant=no_negatives
    ```

- Run the testing for a specific invariants
    ```cmd
    quint run versions/00/bank/bank.qnt --invariants=no_negatives 
    ```

- Verify a temporal proposition with either apalache server or TLC [Model Checkers \| Quint Docs](https://quint.sh/docs/model-checkers)
    ```cmd
    cmd /c verify.cmd versions/01/batch/batch.qnt --backend tlc --temporal=pending_ack_is_eventually_cleared
    ```
    
    - Optional: `--backend tlc` Run the verify with tlc. This will run an unbounded check where all possible states are explored. If it is taking a long time this could mean that there are no violations found in the state exploration or there is a state explosion.
